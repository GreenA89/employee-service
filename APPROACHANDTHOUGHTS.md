# Approach

## Key Decisions

I wanted to include a more true to life persistence source for the employee data to more accurately reflect the benifex
stack. I am aware that you use MongoDB Atlas, however for the purposes of this technical test I thought that would be
overkill and setting up the data source may take too much time away from developing the application functionality iteself.

I opted to use SpringBoot as the REST Framework for the application, both because of its ease of use and relevance to the 
Benifex stack. This was also done future mindedly as I would, given more time, want to auto generate the swagger
documentation for the APIs in the application, and I am aware that SpringBoot contains a Swagger integration where annotations
can be used to document the REST APIs in a 'living' way (i.e. the annotations generate the documentation in real time and
update the documentation if the controllers themselves are updated)

I implemented native jakarta bean validation to validate user input on the server side for the Employee mode. I understand
that it is likely the front end team would also validate the user input on the UI side, however the extra server side validation
adds extra assurance and security to the transaction.

Custom exceptions and a global exception handler were also implemented to add extra context and specific error messaging
to be returned to the client. In a real world scenario these error messages may be useful to the UI / front end developers
to conditionally display UI or the errors themselves, giving a single source of truth to error messaging.

SLF4J logging has also been added to provide server side debugging insight should application errors occur, in a true to 
life example, these would provide observability and monitoring in the cloud kubernetes workloads or compute VMs
and allow easier debugging in the event of application errors.

A healthcheck endpoint was also added for similar reasons, in a true to life example of an application such as this running
in the cloud, observability and monitoring would be set up in the cloud environment to assure the uptime of the application
by polling the healthcheck endpoint regularly. In the event of application downtime, this endpoint would return a non 200 
status code and alert relevant cloud infrastructure staff or the appropriate owning software engineer.

For extra assurance of the unique entry of the email address and id, as requested by the User Story, the email has been 
indexed in the model using the spring / mongo integration `@indexed(unique=true)` annotation, ensuring that the database 
itself will also enforce the unique email requirement in the event that duplicate requests are sent to the endpoint before
the java code can validate an existing entry

## Next Steps

If I had more time available my next steps in building this application
would include, but not be limited to some of the below:

- Add authentication as this is an internal API for use by HR administrators
- Add swagger documentation to assist our front end developers in properly consuming the APIs
    - This can be done easily in SpringBoot using the native controller annotations
- Create integration tests that will test the application and persistence as running holistic entities
    - This has already been stubbed as you can see from `EmployeeServiceIntegrationTest`
    - I would be paying particular attention to validating user input
        - Are invalid user input email addresses rejected
        - Are employee creation requests with a pre-populated ID ignored and a new ID generated by the server regardless
        - Are blank user inputs for necessary fields rejected
        - Are bank user inputs that are not necessary allowed to be blank
- Create an audit table to record transactions on the employee collection
- Enhance the controller / service to allow patching / updating of existing employee records
- Could the enforcement of unique employee IDs be made more robust by rejecting client requests which contain one, rather than overwriting
